<Definition>
**Nearest-neighbour search** returns, for a query $\qvec \in \reals^d$, the $k$ points of a stored set
$\set{\xvec_1, \dots, \xvec_n}$ closest to $\qvec$ under a distance. **Exact** methods return the true neighbours.
**Approximate** methods return points within a factor $c > 1$ of the true nearest distance, or return the true
neighbours with high probability, in exchange for much faster queries.
</Definition>

## Problem

A brute-force query computes all $n$ distances in $O(nd)$ time. For <NoteLink to="k-nearest-neighbours">$k$-nearest
neighbours</NoteLink> on a test set of size $m$ that is $O(mnd)$, and for a similarity join of a set with itself,
$O(n^2 d)$. With a million stored vectors of dimension 768, one query costs about $8 \times 10^8$ multiply-adds.
Search structures built once in advance reduce the per-query cost.

## Mechanism

### Space-partitioning trees

<NoteLink to="space-partitioning-trees">Space-partitioning trees</NoteLink> split the stored points recursively into
regions, each with a lower bound on its distance to a query. A query visits the nearer regions first and skips any
region whose bound exceeds the current $k$-th best distance $r$, so the answer stays exact. A
<NoteLink to="k-d-tree">$k$-d tree</NoteLink> splits at coordinate medians into axis-aligned boxes and needs
coordinates <Cite id="bentley1975" />. A <NoteLink to="ball-tree">ball tree</NoteLink> nests balls and a
<NoteLink to="vantage-point-tree">vantage-point tree</NoteLink> splits at a median distance from a chosen point; both
bound distances by the triangle inequality, so they need only a metric. For fixed dimension the expected query time is
$O(\log n)$ <Cite id="friedman1977" />, but the constant grows exponentially with the dimension: a ball of radius $r$
around the query meets almost every region once $d$ is large, and pruning fails.

### Beyond exact search

In high dimensions no exact index beats a scan by much: Weber, Schek and Blott found that partitioning and clustering
indexes are on average slower than a sequential scan above about 10 dimensions <Cite id="weber1998" />. Search then
becomes <NoteLink to="approximate-nearest-neighbour-search">approximate nearest-neighbour search</NoteLink>, which
returns most of the true neighbours in a small fraction of the time. Its main families have their own notes:
<NoteLink to="locality-sensitive-hashing">locality-sensitive hashing</NoteLink>,
<NoteLink to="inverted-file-index">inverted files</NoteLink>, <NoteLink to="product-quantisation">product
quantisation</NoteLink>, graph indexes such as <NoteLink to="hnsw">HNSW</NoteLink>, and
<NoteLink to="tree-based-approximate-nearest-neighbours">approximate tree search</NoteLink>.

## Cost

| method | build | query | exact? |
| --- | --- | --- | --- |
| brute force | none | $O(nd)$ | yes |
| space-partitioning tree | $O(n \log n)$ | $O(\log n)$ in low intrinsic $d$ | yes |

## Trade-offs

- **Dimension.** Exact trees fail as the <NoteLink to="curse-of-dimensionality-for-neighbours">curse of
  dimensionality</NoteLink> sets in, because almost nothing can be pruned. Above a few tens of dimensions, approximate
  methods or brute force on a <Gloss name="gpu" /> are the practical choices.
- **Metric.** $k$-d trees need coordinates and axis-aligned splits. Ball and vantage-point trees need only a metric, so
  they also serve distances such as edit distance on strings.
- **<NoteLink to="minibatching-and-batch-size">Batch size</NoteLink>.** For many queries at once, a brute-force scan
  written as a <NoteLink to="matrix-multiplication">matrix multiplication</NoteLink> often beats a tree, even in
  moderate dimensions, because it runs at the machine's peak arithmetic rate.
- **Updates.** Trees accept insertions, but many insertions unbalance them and slow queries until they are rebuilt.
