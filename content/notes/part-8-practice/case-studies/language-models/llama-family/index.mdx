## Architecture

All three generations use the same dense decoder-only <NoteLink to="transformer">transformer</NoteLink>. LLaMA took
three changes from earlier models <Cite id="touvron2023b" />:

- **Pre-normalisation with <Gloss name="rmsnorm" />.** Each sub-layer's input is normalised, not its output, using
  root-mean-square <NoteLink to="layer-normalisation">normalisation</NoteLink> <Cite id="zhang2019" />, which rescales
  without subtracting the mean.
- **SwiGLU feed-forward layers** <Cite id="shazeer2020" />, with a hidden dimension of $\frac{2}{3} \cdot 4d$ instead
  of $4d$. SwiGLU has three weight matrices instead of two, so the smaller width keeps the parameter count roughly the
  same.
- **<Gloss name="rope">Rotary position embeddings</Gloss>** <Cite id="su2021" /> instead of absolute
  <NoteLink to="positional-encoding">positional embeddings</NoteLink>. RoPE rotates queries and keys by an angle that
  grows with position, so their dot product depends only on the relative position.

Llama 2 kept this design and changed two things: the context doubled to 4,096 tokens, and the 34B and 70B models use
**<Gloss name="gqa">grouped-query attention</Gloss>** (GQA) <Cite id="touvron2023" /> <Cite id="ainslie2023" />. In GQA,
groups of query heads share one key head and one value head (see <NoteLink to="multi-head-attention">multi-head
attention</NoteLink>). Llama 3 uses GQA with 8 key-value heads at every size, raises the RoPE base frequency to 500,000
to support long contexts, and masks attention between different documents packed into one training sequence
<Cite id="grattafiori2024" />. The 405B model is dense: Llama 3 chose not to use a
<NoteLink to="mixture-of-experts">mixture of experts</NoteLink>, to keep training stable <Cite id="grattafiori2024" />.

## Training

**LLaMA** was trained only on publicly available data: CommonCrawl, C4, GitHub, Wikipedia, books, arXiv and Stack
Exchange, about 1.4T tokens after tokenisation <Cite id="touvron2023b" />. Most data were seen once; Wikipedia and books
were seen about twice. The tokeniser splits numbers into single digits and falls back to bytes for unknown UTF-8
characters. Training the 65B model processed about 380 tokens per second per <Gloss name="gpu" /> on 2,048 A100 GPUs, so
1.4T tokens took about 21 days <Cite id="touvron2023b" />.

**Llama 2** used a new mix of public data, 40% more than LLaMA, and trained every size on 2.0T tokens
<Cite id="touvron2023" />. Pre-training all Llama 2 models used 3.3M GPU hours on A100-80GB hardware.

**Llama 3** trained the 405B model on 15.6T tokens with a 128K vocabulary, first with an 8K context and then in a
long-context phase up to 128K <Cite id="grattafiori2024" />. The standard $6ND$ estimate of training
<Gloss name="flop" plural /> for $N = 405$B parameters and $D = 15.6$T tokens gives $3.8 \times 10^{25}$, the figure the
paper reports.

## What is distinctive

**Training past the compute-optimal point.** <NoteLink to="autoregressive-transformer-language-model">Scaling
laws</NoteLink> fitted by Hoffmann et al. choose model size and data for a fixed training budget, and give roughly 20
training tokens per parameter <Cite id="hoffmann2022" />. They ignore the cost of running the model afterwards. LLaMA's
stated aim was the best model at a given inference budget: a smaller model trained on more tokens is cheaper to serve.
LLaMA reports that a 7B model keeps improving after 1T tokens, where Hoffmann et al. recommend 200B tokens for a 10B
model <Cite id="touvron2023b" />. The ratios:

| Model        | Tokens per parameter |
| ------------ | -------------------- |
| LLaMA 7B     | 149                  |
| LLaMA 65B    | 21                   |
| Llama 2 7B   | 286                  |
| Llama 2 70B  | 29                   |
| Llama 3 405B | 39                   |

Llama 3's own scaling-law fit predicted a compute-optimal 402B model trained on 16.55T tokens for its
$3.8 \times 10^{25}$ FLOP budget, close to the 405B model on 15.6T tokens that was trained. The smaller Llama 3 models
were trained for much longer than compute-optimal <Cite id="grattafiori2024" />.

**Open weights.** All three generations released their weights, and LLaMA reported that its 13B model outperformed
<Gloss name="gpt-3" /> (175B) on most of its benchmarks <Cite id="touvron2023b" />.

## Comparison

**Data grew faster than model size.** From LLaMA 65B to Llama 3 405B, parameters grew 6.2 times and training tokens 11
times.

**The KV cache shrank per parameter.** Multi-head attention caches a key and a value for every head, every layer and
every past token. LLaMA 65B caches $2 \times 80 \times 8{,}192 = 1{,}310{,}720$ numbers per token. Llama 3 70B has the
same depth, width and 64 query heads, but its 8 key-value heads of dimension 128 cache
$2 \times 80 \times 8 \times 128 = 163{,}840$: 8 times less (see <NoteLink to="key-value-cache">KV cache</NoteLink>).
Llama 3 405B, over six times larger than LLaMA 65B, caches $2 \times 126 \times 8 \times 128 = 258{,}048$ numbers per
token, a fifth of LLaMA 65B's.

**Tokeniser.** On a sample of English text, the 128K vocabulary of Llama 3 averages 3.94 characters per token against
3.17 for the 32K vocabulary of Llama 2, so the same training compute covers about 24% more text
<Cite id="grattafiori2024" />. The 28K added tokens also improve compression for languages other than English. A larger
vocabulary costs parameters in the embedding and output layers, which is small next to 405B.

**Context.** Context grew from 2K to 4K to 128K tokens. RoPE carries relative position, and a larger base frequency
slows the rotation, so distant positions remain distinguishable over longer sequences.

**What stayed fixed.** Pre-norm RMSNorm, SwiGLU, RoPE and a dense decoder-only stack appear in all three generations.
The changes between generations are in data, context length, tokeniser and attention sharing, not in the block design.
