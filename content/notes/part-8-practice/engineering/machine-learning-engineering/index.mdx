<Definition>
**Machine learning engineering** covers what it takes to train a model on real hardware, run it at acceptable cost and
keep it working once it serves users. It treats the model as a computation with memory, bandwidth and latency budgets,
and as a component of a system that changes over time.
</Definition>

## What it is for

The methods of Parts IV to VI assume that a model can be trained and evaluated. At current scales that
assumption fails without engineering: a large model does not fit on one accelerator, a trained model is too slow or
costly to serve, and a deployed model degrades as its inputs change. In a production system the model code is a small
part of the whole, and much of the maintenance cost lies in the data, serving and monitoring around it
<Cite id="sculley2015" />.

## Main ideas

**Training is limited by memory and communication.** <NoteLink to="training-at-scale" /> starts from where
<NoteLink to="memory-footprint-of-training">training memory</NoteLink> goes: weights, gradients, optimiser state and
activations. <NoteLink to="mixed-precision-training">Mixed precision</NoteLink> reduces the bytes per number.
<NoteLink to="data-parallelism">Data parallelism</NoteLink> splits each mini-batch across devices, <Gloss name="zero" />
shards the redundant optimiser state, and tensor and <NoteLink to="model-parallelism">pipeline parallelism</NoteLink>
split the model itself <Cite id="narayanan2021" />. <Gloss name="moe">Mixture-of-experts</Gloss> layers grow the
parameter count without growing the computation per token.

**Inference is limited by memory bandwidth.** Generating each token of a <Gloss name="language-model">language
model</Gloss> reads every weight once. <NoteLink to="efficient-inference" /> reduces the bytes read, by quantisation and
pruning, or the model size, by distillation. <Gloss name="flashattention" /> reorganises attention to avoid writing its
score matrix to main memory, and batching shares each read of the weights across many requests.

**Deployment is limited by what changes after release.** <NoteLink to="deployment-and-monitoring" /> releases a model in
stages, first in shadow and then to a small canary share of traffic. Once the model is live, monitoring watches its
service health, inputs, predictions and accuracy, and <NoteLink to="drift-detection">drift detection</NoteLink> tests
whether recent inputs still resemble the reference data.

**One budget, three phases.** The same quantities recur throughout: bytes per parameter, bytes moved per step, and
devices communicating. Mixed-precision formats appear in training and quantisation, and the memory of the
<Gloss name="kv-cache">key-value cache</Gloss> links attention design to serving throughput. Decisions made for training
constrain inference and deployment.

## How the notes fit together

The three subtopics follow a model's life: <NoteLink to="training-at-scale" />, then
<NoteLink to="efficient-inference" />, then <NoteLink to="deployment-and-monitoring" />. Each opens with its own
overview. The training and inference subtopics share hardware concepts and are best read in that order. The deployment
subtopic is mostly statistical and can be read on its own.
