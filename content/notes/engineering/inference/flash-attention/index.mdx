<Definition>
FlashAttention is an algorithm for exact <NoteLink to="scaled-dot-product-attention">scaled dot-product attention</NoteLink>
$\Omat = \operatorname{softmax}\paren{\Qmat \Kmat^\tr / \sqrt{d}} \Vmat$ that splits $\Qmat$, $\Kmat$ and $\Vmat$ into
blocks, loads each block into fast on-chip memory, and combines the partial results with an online softmax. It never
writes the $N \times N$ matrix of scores or probabilities to the GPU's main memory, and it recomputes them in the
backward pass instead of storing them <Cite id="dao2022" />.
</Definition>

## Problem

A GPU has a large, slow main memory (high-bandwidth memory, HBM) and a small, fast on-chip memory (SRAM) next to the
arithmetic units. An NVIDIA A100 has 40–80 GB of HBM with a bandwidth of 1.5–2.0 TB/s, and 192 KB of SRAM in each of 108
streaming multiprocessors with a bandwidth of about 19 TB/s <Cite id="dao2022" />. An operation whose run time is set
by moving data between the two, not by arithmetic, is **memory-bound**.

Standard attention on a sequence of $N$ tokens with head width $d$ runs three steps, each reading its inputs from HBM
and writing its output back:

1. $\Smat = \Qmat \Kmat^\tr / \sqrt d$, an $N \times N$ matrix;
2. $\Pmat = \operatorname{softmax}(\Smat)$, row by row, another $N \times N$ matrix;
3. $\Omat = \Pmat \Vmat$, an $N \times d$ matrix.

Steps 1 and 3 read and write $\Theta(Nd + N^2)$ numbers and step 2 reads and writes $\Theta(N^2)$. For $N \gg d$ the
$N^2$ terms dominate, and the softmax does only a few arithmetic operations per number it moves. The $N \times N$
matrices also dominate memory: for $N = 4096$ in 16-bit precision, $\Smat$ takes 32 MiB per head and per sequence, and
8 GiB for a batch of 8 sequences with 32 heads. The backward pass needs $\Pmat$ again, so standard implementations keep
it.

Splitting the computation into blocks along the key dimension is easy for $\Qmat \Kmat^\tr$ and for $\Pmat \Vmat$, but
the softmax normalises each row over all $N$ keys. The obstacle is to compute a row-wise softmax without first seeing
the whole row.

## Mechanism

### The online softmax

Take one row of scores $s_1, \dots, s_N$ and values $\vvec_1, \dots, \vvec_N$. The output is

$$
\ovec = \frac{\sum_j e^{s_j - m} \vvec_j}{\sum_j e^{s_j - m}}, \qquad m = \max_j s_j,
$$

where subtracting the maximum $m$ changes nothing mathematically and keeps every exponential at most 1, so none
overflows (see <NoteLink to="softmax-and-log-sum-exp">softmax and log-sum-exp</NoteLink>).

Split the keys into blocks. For a block $B$ keep three running quantities: its maximum $m_B = \max_{j \in B} s_j$, its
normaliser $\ell_B = \sum_{j \in B} e^{s_j - m_B}$ and its unnormalised output
$\avec_B = \sum_{j \in B} e^{s_j - m_B} \vvec_j$.
Two disjoint blocks $A$ and $B$ merge as follows. Let $m = \max(m_A, m_B)$. Every term of $\ell_A$ carries the factor
$e^{-m_A}$, and multiplying by $e^{m_A - m}$ turns it into $e^{-m}$:

$$
e^{m_A - m} \ell_A = \sum_{j \in A} e^{s_j - m}.
$$

The same holds for $B$ and for the output sums, so

$$
\ell_{A \cup B} = e^{m_A - m} \ell_A + e^{m_B - m} \ell_B, \qquad
\avec_{A \cup B} = e^{m_A - m} \avec_A + e^{m_B - m} \avec_B.
$$

Both are exactly the quantities that the union would have produced in one pass. By induction over blocks, processing
the keys block by block and merging after each one gives $\ell$ and $\avec$ for the whole row, and $\ovec = \avec / \ell$.
The rescaling factors are at most 1, because $m$ is the larger maximum. Milakov and Gimelshein introduced the running
normaliser for the softmax alone <Cite id="milakov2018" />; FlashAttention carries the output sum $\avec$ along with it
<Cite id="dao2022" />.

### Worked example

One query has scores $(1, 3, 2, 5)$ against four keys with scalar values $(10, 20, 30, 40)$, split into blocks of two.

- Block $A$ (keys 1–2): $m_A = 3$, $\ell_A = e^{-2} + 1 = 1.1353$, $a_A = 10e^{-2} + 20 = 21.353$.
- Block $B$ (keys 3–4): $m_B = 5$, $\ell_B = e^{-3} + 1 = 1.0498$, $a_B = 30e^{-3} + 40 = 41.494$.
- Merge: $m = 5$, and $A$ is rescaled by $e^{3 - 5} = 0.1353$. Then $\ell = 0.1353 \times 1.1353 + 1.0498 = 1.2034$ and
  $a = 0.1353 \times 21.353 + 41.494 = 44.383$.
- Output: $a / \ell = 36.88$, equal to $\operatorname{softmax}(1, 3, 2, 5) \cdot (10, 20, 30, 40)$ computed directly.

Normalising each block separately would give $18.81$ and $39.53$; their plain average, $29.17$, is wrong because the
blocks' normalisers differ.

### Tiling

FlashAttention splits $\Kmat$ and $\Vmat$ into blocks of $B_c$ rows and $\Qmat$ and $\Omat$ into blocks of $B_r$ rows.
For each block of keys and values loaded into SRAM, it loops over the query blocks: it computes the $B_r \times B_c$
block of scores on chip, updates each row's running $m$, $\ell$ and output with the merge rule, and writes the updated
output block back. The $N \times N$ matrices exist only one small block at a time <Cite id="dao2022" />.

The backward pass needs $\Pmat$. FlashAttention stores only $m$ and $\ell$ for each row, $O(N)$ numbers, and recomputes
each block of $\Smat$ and $\Pmat$ from $\Qmat$ and $\Kmat$ when it is needed. This is
<NoteLink to="gradient-checkpointing">recomputation</NoteLink> applied inside one operation. It adds arithmetic but
removes the $\Theta(N^2)$ reads of a stored $\Pmat$, so the backward pass is faster as well as smaller.

### IO complexity

Let $M$ be the size of SRAM in numbers, with $d \le M \le Nd$. A block of $B_c$ keys with $d$ entries each must fit in
SRAM, so $B_c = \Theta(M/d)$; likewise for the query block, and the $B_r \times B_c$ score block must fit too
<Cite id="dao2022" />.

- Each element of $\Kmat$ and $\Vmat$ is loaded once: $\Theta(Nd)$ reads.
- There are $T_c = N / B_c = \Theta(Nd/M)$ key blocks. For each one the inner loop reads all of $\Qmat$ and reads and
  writes all of $\Omat$: $\Theta(Nd)$ per key block.

The total is $\Theta(Nd \cdot Nd/M) = \Theta(N^2 d^2 / M)$ HBM accesses, against $\Theta(Nd + N^2)$ for standard
attention. The ratio is about $M / d^2$. With 96K 16-bit numbers of SRAM per multiprocessor, $M / d^2$ is 6 for
$d = 128$ and 24 for $d = 64$. Dao et al. also prove that no exact attention algorithm can use asymptotically fewer HBM
accesses for all $M$ in this range <Cite id="dao2022" />.

The arithmetic count is unchanged, $\Theta(N^2 d)$, and extra memory is $O(N)$ instead of $O(N^2)$. Rabe and Staats
independently showed with the same rescaling idea that self-attention needs only $O(\log N)$ extra memory in
principle, and gave a practical $O(\sqrt N)$ implementation, without optimising for GPU memory traffic
<Cite id="rabe2021" />.

## Cost

FlashAttention trained BERT-large 15% faster than the MLPerf 1.1 record, GPT-2 at sequence length 1K three times faster
than standard implementations, and made sequence lengths of 16K practical, and 64K with a block-sparse variant
<Cite id="dao2022" />.
FlashAttention-2 reorders the loops so that the outer loop runs over query blocks, which removes the repeated writes of
$\Omat$, parallelises over the sequence dimension and moves non-matrix-multiply work out of the inner loop. It runs about
twice as fast as the first version and reaches 50–73% of the A100's peak throughput in the forward pass
<Cite id="dao2023" />.

## Trade-offs

- **Exact, not approximate.** FlashAttention returns the same result as standard attention up to floating-point
  rounding order. It does not change the $\Theta(N^2 d)$ arithmetic, unlike sparse or low-rank attention, which
  approximate the result.
- **Recomputation for bandwidth.** The backward pass does more arithmetic in exchange for fewer memory accesses. On
  memory-bound hardware this is a net gain.
- **Hardware-specific kernels.** Block sizes depend on SRAM size, and a fast kernel is written for each GPU generation
  and head width. Masks, dropout and positional biases must be fused into the kernel, because the scores never leave
  the chip.
- **Decoding.** During autoregressive decoding with a <NoteLink to="kv-cache">KV cache</NoteLink>, each step has one
  query row, so there is no $N \times N$ matrix to avoid. The time per step is set by reading the cache; splitting the
  cache across blocks processed in parallel and merging them with the same rule helps there.

## Pitfalls

- **Merging normalised outputs.** Partial outputs from different blocks must be merged through their maxima and
  normalisers; averaging normalised outputs is wrong, as the worked example shows.
- **Returning the log-sum-exp.** Code that needs the attention probabilities, for example to visualise them, cannot get
  them from FlashAttention without recomputing them.
- **Mask semantics.** A row whose keys are all masked has $\ell = 0$; kernels must define its output, usually zero, to
  avoid dividing by zero.
