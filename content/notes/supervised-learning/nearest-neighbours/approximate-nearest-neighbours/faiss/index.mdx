<Definition>
**FAISS** is an open-source C++ library with Python bindings, from Meta's Fundamental AI Research group, for searching,
clustering, compressing and transforming dense vectors <Cite id="douze2024" />. Every index exposes the same
operations: `train` on sample vectors, `add` vectors, and `search` for the $k$ nearest neighbours of a batch of queries
under Euclidean distance or <NoteLink to="dot-product">inner product</NoteLink>. Indexes are built by composing a small set of components, and the **index
factory** constructs them from a comma-separated string. Its <Gloss name="gpu" /> implementation is described by Johnson, Douze and Jégou
<Cite id="johnson2019" />.
</Definition>

## Problem

The methods for approximate search, <NoteLink to="inverted-file-index">inverted files</NoteLink>,
<NoteLink to="product-quantisation">product quantisation</NoteLink> and its variants,
<NoteLink to="hnsw">graphs</NoteLink> and <NoteLink to="scalar-quantisation-and-binary-codes">scalar and binary
codes</NoteLink>, combine in many ways, and the best combination depends on dataset size, memory budget, recall target
and hardware. Each combination written from scratch would need its own training, storage, search and GPU code. FAISS
factors them into interchangeable parts that share one interface, so that choosing an index is a matter of changing a
string and measuring.

## Mechanism

### Components

An index built by the factory is a pipeline of up to four parts <Cite id="douze2024" />.

1. **Vector transform** (optional): a rotation or projection applied to queries and data, such as `PCA64`, `OPQ16_64`
   (learn an <NoteLink to="optimised-product-quantisation">OPQ</NoteLink> rotation for 16 sub-quantisers with output
   dimension 64), or `RR64` (a random rotation in 64 dimensions).
2. **Coarse quantiser** (optional): the partition of an inverted file, `IVF4096` for 4096 k-means centroids searched
   exhaustively, or `IVF65536_HNSW32` for 65 536 centroids searched with an HNSW graph. `IMI2x10` is an inverted
   multi-index with $2^{10} \times 2^{10}$ cells. A graph index, `HNSW32` or `NSG32`, takes this place for graph search.
3. **Encoding**: how each vector is stored. `Flat` keeps float32; `SQ8`, `SQ4` and `SQfp16` are scalar quantisers;
   `PQ16` is product quantisation with 16 one-byte codes; `PQ16x12` uses 12-bit codes; `PQ32x4fs` is 4-bit PQ laid out
   for fast-scan; `RQ` and `LSQ` are <NoteLink to="additive-and-residual-quantisation">additive quantisers</NoteLink>.
   Inside an IVF, codes encode the residual from the cell centroid by default.
4. **Refinement** (optional): `RFlat` re-ranks the top $k \cdot k_{\text{factor}}$ candidates with exact distances
   from a stored copy of the vectors; `Refine(SQ8)`, as in `IVF4096,PQ16,Refine(SQ8)`, re-ranks with a finer code instead. Jégou et al. introduced this
   re-ranking with a second, finer code for billion-scale search <Cite id="jegou2011b" />.

### Reading factory strings

| string                               | meaning                                                                                        |
| ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `Flat`                               | exact search over float32 vectors                                                              |
| `IVF4096,Flat`                       | 4096 k-means cells, full vectors in the lists                                                  |
| `IVF4096,PQ64`                       | IVFADC: 4096 cells, residuals coded in 64 bytes                                                |
| `HNSW32`                             | HNSW with 32 links per node, full vectors                                                      |
| `IVF65536,SQ8`                       | 65 536 cells, one byte per dimension                                                           |
| `OPQ16_64,IVF65536_HNSW32,PQ16x4fs`  | OPQ rotation to 64 dimensions, 65 536 cells found by HNSW, 16 four-bit codes scanned with SIMD |
| `PCA160,IVF20000_HNSW,PQ20x10,RFlat` | <Gloss name="pca" /> to 160 dimensions, HNSW-searched IVF, 20 ten-bit codes, exact re-ranking                   |

The last row is the example given in the FAISS paper <Cite id="douze2024" />. The factory strings and their meanings
above follow the FAISS wiki <Cite id="faissdocs" />.

### PQ fast-scan

Product quantisation with 256 centroids per sub-quantiser looks up each code in a table held in cache, one
data-dependent load at a time. **Fast-scan** uses 16 centroids (4 bits) per sub-quantiser, so a table has 16 entries.
The entries are quantised to 8 bits, and a table of 16 bytes fits in one 128-bit SIMD register. The look-up for many
codes at once becomes a single in-register shuffle instruction <Cite id="andre2015" /> <Cite id="andre2017" />
<Cite id="andre2019" />. FAISS implements this as `PQ...x4fs`, stores the codes in blocks of 32 vectors so that
one register load serves a whole block, and uses it inside IVF (`...x4fsr` encodes residuals).

### GPU search

Johnson, Douze and Jégou implemented exact search, IVF-Flat and IVF-PQ on Nvidia GPUs <Cite id="johnson2019" />. The
bottleneck after the distance computations is **k-selection**, keeping the $k$ smallest of many distances. Their
**WarpSelect** keeps small per-thread queues in registers and merges them across the 32 lanes of a warp with odd-size
sorting and merging networks, touching slow memory as little as possible. The paper reports k-selection at up to 55% of
the GPU's theoretical peak, <NoteLink to="nearest-neighbour-search">nearest-neighbour search</NoteLink> 8.5 times faster than the previous GPU state of the art, a <Gloss name="knn" />
graph over 95 million YFCC100M images in 35 minutes, and a graph over 1 billion vectors in under 12 hours on 4 Maxwell
Titan X GPUs <Cite id="johnson2019" />.

### Tuning search parameters

Many indexes have several search-time parameters, for example nprobe of the IVF and efSearch of an HNSW coarse
quantiser. FAISS's `ParameterSpace` enumerates their combinations, measures speed and accuracy on held-out queries,
and keeps only the **Pareto-optimal** settings: those no other setting beats in both speed and accuracy. Its
`OperatingPoints` object prunes settings that a previous measurement already dominates, so the exploration avoids the
full Cartesian product <Cite id="douze2024" />.

## Worked example

This script, run with `uv run --with faiss-cpu --with numpy` (faiss-cpu 1.15.1) on an Apple M1 Pro, builds nine indexes
over 100 000 vectors of dimension 64 drawn from 256 Gaussian clusters, and searches 1 000 queries for their 10 nearest
neighbours on one thread.

```python
import time

import faiss
import numpy as np

rng = np.random.default_rng(0)
n, nq, d, k = 100_000, 1_000, 64, 10

# Synthetic data: a mixture of 256 Gaussian clusters with decaying, rotated per-axis spread
centres = rng.normal(size=(256, d))
scale = 0.05 + 0.6 * np.exp(-np.arange(d) / 16)
rotation, _ = np.linalg.qr(rng.normal(size=(d, d)))


def draw(m):
    noise = rng.normal(size=(m, d)) * scale
    return (centres[rng.integers(256, size=m)] + noise @ rotation.T).astype("float32")


xb, xq = draw(n), draw(nq)
exact = faiss.IndexFlatL2(d)
exact.add(xb)
_, truth = exact.search(xq, k)


def run(factory, **params):
    index = faiss.index_factory(d, factory)
    faiss.omp_set_num_threads(8)  # build with 8 threads
    index.train(xb)
    index.add(xb)
    for name, value in params.items():  # search-time parameters, e.g. nprobe or efSearch
        try:
            faiss.ParameterSpace().set_index_parameter(index, name, value)
        except RuntimeError:  # a parameter the auto-tuner does not know, such as k_factor
            setattr(faiss.downcast_index(index), name, value)
    faiss.omp_set_num_threads(1)  # time the search on one thread
    start = time.perf_counter()
    _, ids = index.search(xq, k)
    qps = nq / (time.perf_counter() - start)
    r1 = np.mean(ids[:, 0] == truth[:, 0])
    r10 = np.mean([len(set(a) & set(b)) / k for a, b in zip(ids, truth)])
    print(factory, params, "1-R@1 %.3f  10-R@10 %.3f  %.0f QPS" % (r1, r10, qps))


run("Flat")
run("IVF1024,Flat", nprobe=4)
run("HNSW32", efSearch=64)
run("SQ8")
run("IVF1024,PQ16", nprobe=16)
run("OPQ16,IVF1024,PQ16", nprobe=16)
run("IVF1024,PQ16,RFlat", nprobe=16, k_factor=4)
run("IVF1024,PQ32x4fsr", nprobe=16)
run("LSH")
```

The output, with the memory each index stores per vector added:

| index                | parameters          | 1-recall@1 | 10-recall@10 | QPS    | bytes per vector |
| -------------------- | ------------------- | ---------- | ------------ | ------ | ---------------- |
| `Flat`               |                     | 1.000      | 1.000        | 1 696  | 256              |
| `IVF1024,Flat`       | nprobe 4            | 0.990      | 0.977        | 84 100 | 256 + 8          |
| `HNSW32`             | efSearch 64         | 0.983      | 0.983        | 22 800 | 256 + 256        |
| `SQ8`                |                     | 0.948      | 0.971        | 778    | 64               |
| `IVF1024,PQ16`       | nprobe 16           | 0.631      | 0.767        | 25 133 | 16 + 8           |
| `OPQ16,IVF1024,PQ16` | nprobe 16           | 0.667      | 0.779        | 25 140 | 16 + 8           |
| `IVF1024,PQ16,RFlat` | nprobe 16, $k_{\text{factor}}$ 4 | 1.000 | 0.999 | 23 223 | 16 + 8 + 256  |
| `IVF1024,PQ32x4fsr`  | nprobe 16           | 0.587      | 0.731        | 28 050 | 16 + 8           |
| `LSH`                | 64 bits             | 0.031      | 0.139        | 11 918 | 8                |



- The inverted file with full vectors is about 50 times faster than exact search at 0.99 1-recall@1 on this clustered data.
- `SQ8` loses little recall at a quarter of the memory, but is slower than `Flat`: the exact scan of a batch of queries
  runs as one <NoteLink to="matrix-multiplication">matrix multiplication</NoteLink>, while `SQ8` decodes vector by vector.
- 16-byte PQ codes cap recall near 0.63. Re-ranking the best 40 candidates with exact vectors (`RFlat`) restores it to
  1.000 while QPS falls from 25 133 to 23 223, but brings back the full vectors' memory, which in practice may sit on disk.
- The OPQ rotation adds about 0.04 to 1-recall@1 at the same code size.
- Random-projection <Gloss name="lsh" /> with 64 bits, compared by Hamming distance over all codes, is far less accurate than learnt codes
  of the same size.

Timings vary by about 20% between runs. The <NoteLink to="approximate-nearest-neighbour-benchmarking">benchmarking note</NoteLink> sweeps nprobe
and efSearch on the same data.

## Cost

- **Choosing by scale.** The FAISS guidelines suggest $k'$ between $4\sqrt n$ and $16\sqrt n$ lists, with an HNSW coarse
  quantiser from about a million vectors: `IVF65536_HNSW32` up to 10 million, `IVF262144_HNSW32` up to 100 million
  and `IVF1048576_HNSW32` up to a billion <Cite id="faissdocs" />.
- **Memory of HNSW.** $(4d + 8M)$ bytes per vector for `HNSW` with $M$ links <Cite id="faissdocs" />.
- **Training data.** Between $30k'$ and $256k'$ vectors for $k'$ centroids <Cite id="faissdocs" />.
- **Scale in practice.** The FAISS paper describes an index of 1.5 trillion 144-dimensional vectors, each compressed to
  54 bytes by a PCA to 72 dimensions and a 6-bit scalar quantiser, with an HNSW coarse quantiser over 10 million
  centroids, sharded over a distributed file system and searched in about one second per query
  <Cite id="douze2024" />.

## Trade-offs

- **Composability over peak speed.** A specialised library can beat a FAISS index on one benchmark. FAISS makes every
  combination of transform, partition, encoding and refinement available behind one interface, with GPU versions of
  the most used ones.
- **Batch-oriented.** Search is fastest on batches of queries, which use matrix multiplication and multiple threads.
  Single-query latency is lower with graph indexes.
- **No metadata.** FAISS stores vectors and integer ids only. Filtering, persistence and replication belong to the
  database built around it; a selector can restrict search to a subset of ids.
- **Deletion** is cheap in flat and IVF indexes and not supported efficiently in HNSW.
