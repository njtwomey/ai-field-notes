<Definition>
A **graph index** for <NoteLink to="nearest-neighbour-search">nearest-neighbour search</NoteLink> is a directed graph whose nodes are the stored vectors. A query is
answered by **greedy beam search**: start from a fixed entry node, keep a list of the $L$ closest nodes seen, repeatedly
expand the closest unexpanded one by computing distances to its out-neighbours, and stop when every node in the list has
been expanded <Cite id="subramanya2019" />. Graph families differ in how they choose each node's out-neighbours:
enough, and in enough directions, for routing to succeed, but few enough to keep memory and per-hop cost low.
</Definition>

## Intuition

Greedy routing succeeds if, from any node, some neighbour is closer to the target. Linking each point to its $k$ nearest
neighbours fails this test in two ways. On clustered data all $k$ links stay inside the point's cluster, so the search
can be trapped. On spread-out data the $k$ links point roughly the same way, so the search moves in short steps and
needs many hops. Good graphs link each point to near neighbours in many different directions, plus some long links for
fast travel. Every method below is a rule for choosing such links, and a construction algorithm that applies the rule
without computing all $n^2$ distances.

## Details

### The relative neighbourhood rule

The **relative neighbourhood graph** (RNG) joins $\pvec$ and $\qvec$ exactly when no third point $\rvec$ is closer to
both of them than they are to each other <Cite id="toussaint1980" />:

$$
\text{edge } (\pvec, \qvec) \iff \nexists\, \rvec:\ \max\big(D(\pvec, \rvec), D(\qvec, \rvec)\big) < D(\pvec, \qvec).
$$

An edge is removed when a shorter two-hop route via $\rvec$ exists. Graph indexes apply a greedy version of this test
when choosing the out-neighbours of $\pvec$ from a candidate list. Sort the candidates by distance from $\pvec$. Keep
the closest, $\pvec^*$. Discard every remaining candidate $\pvec'$ that is closer to $\pvec^*$ than to $\pvec$, since
$\pvec'$ lies behind $\pvec^*$ as seen from $\pvec$ and is reachable through it. Repeat with the closest survivor. The
result is the **sparse neighbourhood graph** described by DiskANN's authors <Cite id="subramanya2019" />. <Gloss name="hnsw" />'s
neighbour selection heuristic <Cite id="malkov2018" /> and NSG's edge selection <Cite id="fu2019" /> are forms of
this rule.

If every node's out-neighbours are chosen this way from all other points, greedy search for any stored point
$\xvec_q$ reaches it. At a node $\pvec$ that does not link to $\xvec_q$, the point $\xvec_q$ was discarded because some
kept neighbour $\pvec^*$ satisfied $D(\pvec^*, \xvec_q) \le D(\pvec, \xvec_q)$. So there is always a neighbour at
least as close to the target. The guarantee says nothing about the number of hops, though. For points spaced along a
line, the rule links each point only to its two adjacent points, and a search crosses the line one point at a time.

### Vamana and $\alpha$-pruning

**Vamana**, the graph inside DiskANN, relaxes the discard test with a factor $\alpha \ge 1$
<Cite id="subramanya2019" />. Its **RobustPrune** procedure keeps the closest candidate $\pvec^*$ and discards a
candidate $\pvec'$ only if

$$
\alpha \cdot D(\pvec^*, \pvec') \le D(\pvec, \pvec'),
$$

stopping when $\pvec$ has $R$ out-neighbours. With $\alpha = 1$ this is the rule above. With $\alpha > 1$ a candidate
survives unless $\pvec^*$ is $\alpha$ times closer to it than $\pvec$ is. Fewer candidates are discarded, and the extra
survivors are the ones far from $\pvec$ that a kept neighbour only moderately covers: long edges.

The same argument as before now gives geometric progress. At a node $\pvec$ that does not link to the target $\xvec_q$,
some kept neighbour satisfies $D(\pvec^*, \xvec_q) \le D(\pvec, \xvec_q)/\alpha$. Greedy search moves to the neighbour
closest to the target, which is at least this close. After $s$ steps the distance is at most $\Delta/\alpha^s$, where
$\Delta$ is the starting distance. If $\delta$ is the smallest distance between two stored points, the search reaches
the target within $\log_\alpha(\Delta/\delta)$ steps. The authors state the property for a graph pruned over all
points; Vamana applies RobustPrune to the candidates visited by a search, which approximates it at far lower cost
<Cite id="subramanya2019" />.

Vamana builds the graph in two passes over the data, both starting from the medoid. The first pass uses $\alpha = 1$
and the second a larger $\alpha$ that adds long-range edges. The DiskANN paper uses $\alpha = 2$ with degree bound
$R$ between 64 and 128 and search list size $L = 125$ during construction; FreshDiskANN uses $\alpha = 1.2$ and finds
little gain beyond it <Cite id="subramanya2019" /> <Cite id="singh2021" />.

### DiskANN: graphs on SSD

Graph search in RAM is fast, but a billion 128-dimensional float vectors with their links need several hundred GB.
DiskANN keeps the graph and the full-precision vectors on a solid-state drive (SSD), and only
<NoteLink to="product-quantisation">product-quantisation</NoteLink> codes in RAM <Cite id="subramanya2019" />.

- The product-quantisation (PQ) codes guide the search: they estimate which nodes to expand next without reading the disk.
- **Beam search** reads the neighbourhoods of the $W$ best frontier nodes in one round of parallel SSD reads. Small
  widths such as $W = 4$ balance latency and throughput.
- A node's full vector is stored in the same 4 KB sector as its adjacency list, so reading a neighbourhood also fetches
  the exact vector. The final results are re-ranked with exact distances at no extra I/O.
- Vamana's long edges reduce the number of hops, which matters more on disk than in RAM because each hop costs a round trip to the SSD.

On the billion-point <NoteLink to="meta-vector-search-research">SIFT1B</NoteLink> dataset, DiskANN reports more than 5000 <NoteLink to="approximate-nearest-neighbour-benchmarking">queries per second</NoteLink> with mean latency under 3 ms and
1-recall@1 above 95%, on a 16-core workstation with 64 GB of RAM and an SSD <Cite id="subramanya2019" />.

**FreshDiskANN** supports insertions and deletions. A deleted point goes on a delete list and is still used for
navigation but filtered from results. After 1 to 10% of the index has been deleted, a batch step gives every node that
pointed to a deleted node that node's out-neighbours as extra candidates and re-prunes with RobustPrune
<Cite id="singh2021" />.

**Filtered-DiskANN** builds graphs that remain navigable when a query is restricted to vectors carrying a given label
<Cite id="gollapudi2023" />.

### NSG

The **navigating spreading-out graph** (NSG) of Fu, Xiang, Wang and Cai approximates the **monotonic relative
neighbourhood graph** (MRNG), a sparse graph in which a monotonic path, one that gets closer to the target at every
step, exists between any two nodes and is found by greedy search without backtracking <Cite id="fu2019" />. Building the
MRNG exactly costs too much, so NSG starts from an approximate $k$-nearest-neighbour graph, applies MRNG edge selection
to candidates found by searching it, and fixes one **navigating node**, the approximate medoid, as the start of every
search. A depth-first traversal from the navigating node then adds edges until every node is reachable. NSG has been
integrated into the Taobao (Alibaba) e-commerce search engine at billion-node scale <Cite id="fu2019" />.

### NGT and SPTAG

**NGT** (Yahoo Japan) starts from a $k$-nearest-neighbour graph and adjusts both in-degrees and out-degrees: every node
needs enough incoming edges to be reachable, and excess outgoing edges are removed when an alternative path exists
<Cite id="iwasaki2018" />. **SPTAG** (Microsoft) combines a space-partitioning tree, which finds good entry points, with
a relative neighbourhood graph that the search then walks <Cite id="sptag" />.

## Assumptions

- **A metric that behaves.** The pruning arguments use the triangle inequality. Graph indexes are also used for <NoteLink to="dot-product">inner
  products</NoteLink>, which are not metrics, and then work only empirically (see
  <NoteLink to="maximum-inner-product-search">maximum inner product search</NoteLink>).
- **Queries like the data.** The graph is shaped by the stored points. Queries from a different distribution, such as
  text queries against image embeddings, need more expansions for the same recall.

## Pitfalls

- **Memory for edges.** Degree $R = 64$ with 4-byte ids costs 256 bytes per vector, as much as 64 floats.
- **Construction cost.** Each insertion is a search plus pruning. A billion-point graph takes days to build. DiskANN built
  one in about 2 days on a machine with 1.1 TB of RAM, or in about 5 days on a 64 GB workstation by building 40
  overlapping shards and merging their edges <Cite id="subramanya2019" />.
- **Deletion.** Removing a node can disconnect the graph. Most libraries mark nodes as deleted and skip them, which
  slowly degrades recall until the graph is repaired or rebuilt.
- **Comparisons across papers.** Graph methods differ mainly in pruning and construction details, and rankings change
  with the dataset. Wang et al. compared 13 graph methods in one test environment on 8 real
  and 12 synthetic datasets, and their recommendations of which method to use differ by use case
  <Cite id="wang2021graphsurvey" />.
