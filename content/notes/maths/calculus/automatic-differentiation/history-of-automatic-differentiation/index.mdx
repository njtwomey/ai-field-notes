<Definition>
Automatic differentiation (AD) computes exact derivatives of a program by applying the chain rule to its elementary
operations. Its history has three phases: the first programs and the discovery of forward and reverse modes
(1964–1980), general-purpose tools for scientific computing (1990s–2000s), and machine-learning frameworks (from
about 2010) <Cite id="baydin2018" />. Across all three, tools differ mainly in how they get hold of the program.
</Definition>

## The two modes

**Forward mode, 1964.** Wengert described a program that differentiates a function by evaluating it as a list of
elementary operations, each carrying its value and derivative forward <Cite id="wengert1964" />. Such a list of
intermediate assignments is still called a Wengert list. Forward mode is the arithmetic of
<NoteLink to="dual-numbers">dual numbers</NoteLink> and is covered in
<NoteLink to="forward-mode-autodiff">forward-mode automatic differentiation</NoteLink>.

**Reverse mode, 1970.** Linnainmaa's 1970 master's thesis at the University of Helsinki, on the accumulated <NoteLink to="floating-point-arithmetic">rounding
error</NoteLink> of an algorithm, expressed that error through the derivatives of the final result with respect to every
intermediate, computed by a backward sweep. This is the reverse mode; it was published in English in 1976
<Cite id="linnainmaa1976" />. Griewank's account of who invented reverse mode traces it to this work, with several
later independent rediscoveries <Cite id="griewank2012" />.

**Speelpenning, 1980.** Speelpenning's thesis built a system that read a Fortran-like program and generated a program
for its <NoteLink to="gradient">gradient</NoteLink>, an early reverse-mode source transformation <Cite id="speelpenning1980" />.

**Backpropagation.** Werbos applied reverse-mode differentiation to general nonlinear systems, including neural
networks, in work from his 1974 thesis onward <Cite id="werbos1982" />. Rumelhart, Hinton and Williams popularised it
for training multilayer networks in 1986 as backpropagation <Cite id="rumelhart1986" />, the same computation described
in <NoteLink to="backpropagation">backpropagation</NoteLink>.

## Three ways to see the program

A tool must find out which operations the program performs before it can differentiate them.

- **Operator overloading.** Run the program on special number types whose operations record themselves (on a tape) or
  carry derivatives. The tool sees the operations that actually execute, with their actual values. See
  <NoteLink to="operator-overloading-and-tapes">operator overloading and tapes</NoteLink>.
- **Source transformation.** Read the program's code, or a compiler's intermediate representation of it, and write a
  new program that computes the derivatives. The derivative program can be optimised by a compiler like any other.
  See <NoteLink to="source-transformation-autodiff">source-transformation autodiff</NoteLink>.
- **Computation graphs.** Have the user build, or have the tool trace, an explicit graph of operations, then
  differentiate and optimise the graph. See
  <NoteLink to="static-and-dynamic-computation-graphs">static and dynamic computation graphs</NoteLink>.

## Scientific-computing tools

The first general-purpose tools targeted Fortran and C simulation codes, where derivatives were needed for
sensitivity analysis, optimisation and data assimilation. Griewank and Walther's textbook collects the theory from this
era <Cite id="griewank2008" />.

- **ADIFOR** (1992) generated forward-mode derivative code for Fortran 77 by source transformation
  <Cite id="bischof1992" />.
- **ADOL-C** (1996) differentiated C and C++ by operator overloading, recording a tape at run time and supporting both
  modes and higher derivatives <Cite id="griewank1996" />.
- **TAF** and its predecessor TAMC generated adjoint (reverse-mode) Fortran code for large climate models
  <Cite id="giering1998" />.
- **Tapenade**, descended from the earlier Odyssée tool at INRIA, transforms Fortran and C source in both modes
  <Cite id="hascoet2013" />.

This era also solved the memory problem of reverse mode, which must keep every intermediate value for the backward
sweep; see <NoteLink to="gradient-checkpointing">gradient checkpointing</NoteLink>.

## Machine-learning frameworks

Deep learning made reverse mode the default workload: one scalar loss, millions of parameters, run on <Gloss name="gpu" plural />.

- **Theano** (described in 2010) built a symbolic graph in Python, differentiated it and
  compiled it for <Gloss name="cpu" /> and GPU <Cite id="bergstra2010" />.
- **Chainer** (2015) popularised define-by-run: the graph is recorded as ordinary Python code executes
  <Cite id="tokui2019" />.
- **Autograd** (2015) differentiated plain NumPy code by operator overloading, with a tape recorded at run time
  <Cite id="maclaurin2015" />.
- **TensorFlow** (2015) built static dataflow graphs executed in sessions <Cite id="abadi2016" />. TensorFlow 2 (2019)
  switched to eager execution with a `GradientTape`, and uses `tf.function` to trace graphs.
- **PyTorch** (2017) adopted define-by-run with a tape of `grad_fn` nodes <Cite id="paszke2017" />
  <Cite id="paszke2019" />.
- **Tangent** (2017) differentiated Python functions by source transformation of their syntax trees
  <Cite id="vanmerrienboer2018" />.
- **JAX** (2018) traces Python functions into an intermediate language, then applies composable transformations such as
  `grad`, `jvp`, `vmap` and `jit` <Cite id="bradbury2018" />.
- **Zygote** (2018–19) differentiates Julia code by source transformation of the compiler's SSA form
  <Cite id="innes2018" />.
- **Enzyme** (2020) differentiates LLVM intermediate representation after optimisation, so it works for any language
  that compiles to LLVM <Cite id="moses2020" />.

| ADOL-C | 1996 | C, C++ | forward, reverse | operator overloading, tape | dynamic |
| Tapenade | 2000s | Fortran, C | forward, reverse | source transformation | static |
| Theano | 2010 | Python | reverse | symbolic graph, compiled | static |
| Autograd | 2015 | Python (NumPy) | reverse | operator overloading, tape | dynamic |

| TensorFlow 2 | 2019 | Python | reverse | tape (eager), tracing (`tf.function`) | dynamic or traced |
| Enzyme | 2020 | any LLVM language | forward, reverse | transformation of optimised LLVM IR | static |

"Static" means the derivative is derived from the program's text or graph before it runs; "dynamic" means it is
recorded as the program runs; "traced" means the program is run once on abstract values to capture a graph, which is
then transformed and compiled.

## Flexibility against speed

The approaches trade flexibility against speed. Recording at run time handles any control flow the host language
allows, but the recording costs time on every call and gives a compiler nothing to optimise. Transforming the program
ahead of time produces derivative code as fast as hand-written code, but the tool must understand every language
feature the program uses. Tracing sits between: arbitrary Python runs once to produce a graph, and the graph is
compiled, as long as the control flow does not depend on data. Modern frameworks mix the approaches, eager recording
for development and tracing for speed.

For higher derivatives and <NoteLink to="jacobian">Jacobians</NoteLink> the common interface has converged on two
primitives, the Jacobian-vector and vector-Jacobian products; see
<NoteLink to="jacobian-vector-products-and-higher-order-derivatives">JVPs, VJPs and higher-order derivatives</NoteLink>.
