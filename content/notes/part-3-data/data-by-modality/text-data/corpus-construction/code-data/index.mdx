<Definition>
**Code data** comprises source code, repository structures, commit histories, build scripts, and associated technical
documentation used to train neural code generation models. Unlike natural language prose, source code obeys strict
formal grammars, depends heavily on repository-level dependency graphs, and exhibits extreme levels of cloning due to
open-source forks, vendoring, and autogenerated files. Curating code corpora requires parsing-based syntax validation,
intellectual property and licence attribution, entropy-based secret scanning, and rigorous decontamination against
evaluation benchmarks.
</Definition>

## Forks and vendored duplicates

Public code hosting platforms such as GitHub and GitLab contain massive duplication. Developers routinely fork
repositories to submit pull requests, mirror archived projects, and vendor entire third-party libraries directly into
repository source trees.

Allamanis showed that code duplication severely corrupts machine learning models of code, inflating reported test
accuracies by over $30\%$ due to train-test leakage and causing <Gloss name="language-model">language models</Gloss> to
overfit heavily on repeated boilerplate <Cite id="allamanis2019" />. In constructing *The Stack*, Kocetkov et al. found
that over $70\%$ of raw files collected across 300 programming languages were exact or near-duplicates
<Cite id="kocetkov2022" />:

- **Exact file deduplication:** SHA-256 hashing across canonicalised file bytes strips identical copies across distinct
  forks and branches.
- **<NoteLink to="near-duplicate-detection">Near-duplicate detection</NoteLink>:** Applying MinHash on token
  $w$-shingles collapses files that differ only by minor variable renamings, version bumps, or license header
  insertions.
- **Repository-level deduplication:** Graph-based grouping clusters forks back to their root upstream repository,
  preventing heavily forked repositories from dominating training budgets.

## Licences and governance

Source code is governed by copyright and software licences that impose strict legal conditions on reproduction,
redistribution, and derivative works:

- **Permissive licences (MIT, Apache 2.0, BSD, ISC):** Allow unrestricted copying and derivative use with simple
  copyright and attribution retention. Permissive code forms the backbone of open <Gloss name="llm" /> pretraining
  corpora such as StarCoder and Code Llama <Cite id="li2023starcoder" />.
- **Copyleft licences (GPL, AGPL, LGPL):** Mandate that derivative works or linked applications release their
  corresponding source under identical copyleft terms. Commercial deployers frequently exclude copyleft repositories
  from training sets to avoid copyright contamination.
- **Unlicensed and proprietary code:** Repositories without an explicit open-source licence default to full copyright
  reservation under Berne Convention rules.
- **Attribution and opt-out:** The BigCode project established opt-out indices (such as *Am I in The Stack?*) allowing
  developers to inspect whether their repositories are present and request retroactive deletion from future dataset
  releases.

## Repository context and dependency graphs

Evaluating or training on source code files in isolation strips crucial structural context. A function definition in
`service.py` frequently references classes defined in `models.py`, relies on types imported from installed packages, and
is governed by repository configuration files (`package.json`, `Cargo.toml`, `pyproject.toml`):

- **Repository packing:** Rather than presenting isolated files as independent documents, modern training pipelines
  concatenate all files belonging to a single repository into a unified document context, separated by file path headers
  (`# File: src/main.rs`). This allows cross-attention to resolve imports and internal API signatures.
- **Abstract Syntax Tree (AST) parsing:** Tools like Tree-sitter parse raw source files into syntax trees across dozens
  of programming languages. Filtering candidates by parse success rate discards syntactically corrupt files, truncated
  scrapes, and incomplete snippets.

## Secrets and sensitive data

Developers routinely commit operational secrets into version control by accident. Public repositories contain hundreds
of thousands of active cloud access keys (AWS, GCP, Azure), database passwords, GitHub personal access tokens, and SSH
private keys.

Training language models directly on unscrubbed code risks memorising and regurgitating valid private credentials during
generation. Secret scanning combines two mechanisms:

1. **Regular expression signatures:** High-precision patterns detecting known API token structures (such as
   `AKIA[0-9A-Z]{16}` for AWS access keys).
2. **Shannon entropy filtering:** Measuring the information entropy of alphanumeric string literals:

   $$
   H(S) = -\sum_{c \in \Sigma} p(c) \log_2 p(c).
   $$

   Natural programming variable names have typical entropies between $2.5$ and $3.8$
   <NoteLink to="perplexity-as-a-metric">bits per character</NoteLink>, whereas cryptographically generated API keys and
   hashes typically exceed $4.5$ bits per character. Files containing unredacted secrets are either masked or discarded
   entirely.

## Generated files and boilerplate

Substantial volumes of committed code are produced by compilers and code generators rather than humans:
- Protocol buffer and gRPC stubs (`.pb.go`, `_pb2.py`).
- Minified JavaScript bundles (`.min.js`), where whitespace is stripped and identifiers mangled into single letters.
- Dependency lockfiles (`package-lock.json`, `poetry.lock`).
- Jupyter notebook output cells containing megabytes of raw image base64 strings or stack traces.

Autogenerated code inflates token counts with low-information patterns that do not reflect human software engineering
intent. Heuristic filters check for standard header signatures (`// Code generated by ... DO NOT EDIT`), line length
cutoffs (e.g., maximum line length $\le 1000$ characters), and average token character lengths to isolate and prune
generated files.

## Pitfalls

- **Evaluation <NoteLink to="benchmark-contamination">benchmark contamination</NoteLink>:** Prevalent coding benchmarks
  like HumanEval and MBPP test standard algorithm prompts <Cite id="chen2021" />. Canonical test solutions uploaded to
  public GitHub repositories leak directly into training sets, rendering reported pass@$k$ metrics invalid unless
  decontaminated via strict $n$-gram or AST filtering.
- **Stripping comments and docstrings:** Removing inline comments and docstrings destroys the alignment between natural
  language intent and implementation logic, which models rely on to perform text-to-code synthesis.
- **Failing to pin repository states:** Scraping git repositories at active default branches (`main` or `master`)
  produces non-reproducible training snapshots unless pinned to explicit git commit commit hashes (SHAs).
